### مفاهیم

**`src/` layout** — کد در `src/` است تا از ریشهٔ پروژه قابل import نباشد. پس مجبورید نصبش کنید، و تست‌ها همان چیزی را امتحان می‌کنند که کاربر نصب می‌کند. *اصل کلی: هرچه محیط تست به production نزدیک‌تر، سورپرایز production کمتر.*

**virtualenv** — سه مشکل را حل می‌کند: (۱) dependency hell، وقتی دو پروژه به نسخه‌های متفاوت یک پکیج نیاز دارند؛ (۲) نمی‌دانید پروژه واقعاً به چه چیزی نیاز دارد؛ (۳) ابهام در اینکه کدام interpreter اجرا می‌شود. فعال‌سازی، `.venv\Scripts` را به ابتدای `PATH` می‌برد.

**Docker در برابر virtualenv** — venv فقط پکیج‌های Python را ایزوله می‌کند. Docker کل سیستم‌عامل را بسته‌بندی می‌کند: نسخهٔ Python، کتابخانه‌های سیستمی C، متغیرهای محیطی. به همین دلیل venv روی لپ‌تاپ کار می‌کند ولی روی سرور می‌شکند.

**semantic versioning** — `MAJOR.MINOR.PATCH`. PATCH برای رفع باگ، MINOR برای قابلیت سازگار، MAJOR وقتی چیزی را می‌شکنید. `0.x.x` یعنی هنوز پایدار نیست.

**dependency به‌عنوان بدهی** — هر پکیج باید به‌روز نگه داشته شود، ممکن است آسیب‌پذیری داشته باشد، ممکن است رها شود. `dependencies = []` عمدی بود.

**قید نسخه** — `>=3.12` نه `==3.12`. انعطاف در برابر واقعیت. نسخه‌های دقیق به lock file تعلق دارند، نه به `pyproject.toml`.

**EOL (End Of Life)** — نرم‌افزار تاریخ انقضا دارد. Python 3.10 در اکتبر ۲۰۲۶ منقضی می‌شود. پروژه‌ای که روی runtime منقضی بنا شود، از روز اول technical debt است.

**docstring در برابر comment** — comment با `#` شروع می‌شود و در runtime ناپدید می‌شود. docstring یک رشته است که در حافظه می‌ماند و در `__doc__` قابل دسترسی است.

**smoke test** — کوچک‌ترین تستی که ثابت می‌کند زنجیره سالم است: نصب ← import ← اجرا. اصطلاح از سخت‌افزار: مدار را برق‌دار کن و ببین دود می‌کند یا نه.

**dunder** — `__version__`، `__init__`. دو زیرخط در دو طرف. قرارداد، نه جادو.

## PATH و environment

**ترتیب جست‌وجوی دستور در ویندوز:** اول پوشهٔ فعلی، بعد `PATH` به ترتیب. **اولین** موردی که پیدا شود اجرا می‌شود.

**command hijacking** — چون ویندوز پوشهٔ فعلی را اول می‌گردد، هر کسی که بتواند فایلی آنجا بنویسد، می‌تواند دستورات شما را بدزدد. لینوکس عمداً پوشهٔ فعلی را در `PATH` نمی‌گذارد؛ به همین دلیل آنجا `./script.sh` می‌نویسید.

**environment variables و وراثت** — هر process یک جدول کلید-مقدار دارد. فرزند یک **کپی** از environment والد می‌گیرد. وراثت **یک‌طرفه** است: فرزند نمی‌تواند والد را عوض کند. به همین دلیل `cd` داخل یک script روی shell شما اثر ندارد.

**PowerShell در برابر cmd** — دو زبان متفاوت در یک پنجرهٔ سیاه. در PowerShell، `where` یک alias برای `Where-Object` است، نه `where.exe`. به‌جایش `Get-Command python -All`.

## Git

### سه ناحیه

```
Working Directory  ──git add──▶  Staging Area  ──git commit──▶  Repository
فایل‌های روی دیسک                  (index)                       تاریخچهٔ دائمی
        ◀──git restore --staged──         ◀──git reset──
```

هر ناحیه **نسخهٔ کامل و مستقل خودش** از فایل را دارد. یک فایل می‌تواند همزمان در Staging نسخهٔ ۱ و روی دیسک نسخهٔ ۲ باشد؛ `git status` آن را در **هر دو** بخش نشان می‌دهد.

**چرا staging وجود دارد:** تا بتوانید commit های **اتمیک و معنادار** بسازید — هر commit یک تغییر منطقی. این چیزی است که بعداً `revert`، `cherry-pick` و code review درست را ممکن می‌کند.

### جدول نجات برای secret ها

| وضعیت | ابزار |
|---|---|
| فقط stage شده، commit نشده | `git restore --staged <file>` |
| در آخرین commit، push نشده | `git reset --soft HEAD~1` |
| push شده | **دیر است. revoke کن.** |

`--amend` برای این کار **نیست** — روی آخرین commit کار می‌کند، نه روی staging.

### دستورات

| دستور | کار |
|---|---|
| `git status -u` | همهٔ فایل‌ها، نه خلاصهٔ پوشه‌ها |
| `git diff` | Working Directory در برابر Staging |
| `git diff --staged` | Staging در برابر Repository — **همیشه قبل از commit** |
| `git restore --staged <f>` | از staging بیرون بیاور، دیسک را دست نزن |
| `git commit --amend` | آخرین commit را جایگزین کن |
| `git remote -v` | remote های تنظیم‌شده |
| `git log --oneline` | تاریخچهٔ فشرده |

### مفاهیم

**commit ها immutable اند.** `--amend` commit را ویرایش نمی‌کند؛ یک commit جدید با hash جدید می‌سازد.

**مرز مقدس:** تاریخچهٔ خصوصی (push‌نشده) را آزادانه بازنویسی کن. تاریخچهٔ عمومی (push‌شده) مقدس است.

**سه نوع object:** `blob` محتوای فایل، `tree` یک پوشه، `commit` یک tree ریشه + والد + نویسنده + پیام. **Git پوشه را ردیابی نمی‌کند** — یک tree خالی محتوایی ندارد. به همین دلیل `.gitkeep` لازم است.

**Conventional Commits** — `feat:` `fix:` `docs:` `test:` `refactor:` `chore:`. حالت **امری** (`add` نه `added`)، زیر ۷۲ کاراکتر، توضیح **چرا** نه **چه**.

**`master` → `main`** — از حدود ۲۰۲۰ استاندارد صنعت. `git branch -m main` و `git config --global init.defaultBranch main`.

**سه سطح تنظیمات Git:** `--system` (ماشین)، `--global` (کاربر)، بدون flag (این repo). خاص‌تر بر عام‌تر غلبه می‌کند.

**idempotency** — عملیاتی که اجرای دهم‌بارش همان نتیجهٔ بار اول را بدهد. `git remote add` idempotent **نیست**. در سیستم‌های توزیع‌شده حیاتی است: وقتی شبکه قطع می‌شود و نمی‌دانید درخواست رسیده یا نه، تنها کار ممکن دوباره فرستادن است.

### امنیت

**secret را هرگز از جایی که تایپ می‌شود بیرون نفرست.** نه در چت، نه در ایمیل، نه در screenshot. ربات‌هایی کل GitHub را برای `ghp_` اسکن می‌کنند و ظرف ثانیه‌ها از توکن‌های لو رفته استفاده می‌کنند.

**Credential Manager در برابر توکن دستی:** GCM اعتبارنامه را رمزگذاری‌شده در انبار OS نگه می‌دارد، خودش تمدید می‌کند، و هرگز به صورت متن ساده جابه‌جا نمی‌شود.

### پایان خط

**LF** (`\n`) لینوکس، **CRLF** (`\r\n`) ویندوز.

اگر یک shell script با CRLF داخل کانتینر Linux اجرا شود، `#!/bin/bash\r` می‌شود و خطای `bad interpreter: No such file or directory` می‌دهد — ساعت‌ها وقت تلف‌شده، چون `^M` نامرئی است.

`.gitattributes` بر `core.autocrlf` غلبه می‌کند، چون **داخل repo است و برای همه یکسان اعمال می‌شود**. `binary` برای فایل‌های دودویی از فساد داده جلوگیری می‌کند.

## روش debugging

```
۱. خطا را دقیق بخوان. چه کسی گوینده است؟ (`remote:` یعنی سرور گفته)
۲. فرضیه‌ها را قبل از آزمایش فهرست کن
۳. هر فرضیه را با یک دستور آزمایش کن
۴. رد کن تا یکی بماند
۵. زنجیرهٔ علت را به عقب ردیابی کن
۶. در منبع درست کن، نه در محل بروز
```

**درس‌های سخت:**

- **محل بروز خطا، محل وقوعش نیست.** GitHub گفت "Invalid token" در حالی که مشکل این بود که هیچ توکنی فرستاده نشده بود.
- **مطمئن شو چیزِ درست را اندازه می‌گیری.** اندازه‌گیری روی سوژهٔ اشتباه از حدس زدن خطرناک‌تر است، چون داده داری و به داده اعتماد می‌کنی. همیشه بپرس: این عدد از کدام ماشین، کدام process، کدام لحظه آمده؟
- **«چیزی پیدا نکردم» با «ثابت شد نیست» یکی نیست.**
- **failing silently از failing loudly خطرناک‌تر است.**
- ناهنجاری‌های کوچک را نادیده نگیر. آن `Press any key to continue` امضای یک `python.bat` بود که کل تشخیص را عوض کرد.

## Stage 2 — Python: types و functions 🔄

### type های پایه

| مقدار | type | نکته |
|---|---|---|
| `72.5` | `float` | عدد اعشاری |
| `"PUMP-01"` | `str` | رشته |
| `3` | `int` | عدد صحیح |
| `False` | `bool` | |
| `None` | `NoneType` | **نبودِ مقدار** |

**dynamic typing** — type را اعلام نمی‌کنید؛ Python از مقدار حدس می‌زند، و متغیر می‌تواند type عوض کند. انعطاف، ولی خطرناک.

**`None` با `0` و `""` فرق دارد.** `0` یعنی «دما صفر است». `None` یعنی «دما را نداریم». اگر یکی بگیریدشان، میانگین‌ها دروغ می‌گویند.

### مسئلهٔ اصلی: CSV فقط متن است

```python
float("72.5") + 1   -> 73.5
"72.5" + 1          -> TypeError: can only concatenate str (not "int") to str
float("hello")      -> ValueError: could not convert string to float: 'hello'
float("")           -> ValueError: could not convert string to float: ''
int("72.5")         -> ValueError: invalid literal for int() with base 10: '72.5'
float(" 72.5 ")     -> 72.5      # فاصله‌ها را می‌بخشد
float("nan")        -> nan       # 🚨 بدون اعتراض
```

`nan` هر محاسبه‌ای را که لمسش کند `nan` می‌کند، **بدون هیچ خطایی**.

> **قابل تبدیل بودن با معتبر بودن یکی نیست.** `float()` نمی‌گوید داده سالم است؛ فقط می‌گوید قابل تبدیل بود.

### توابع

```python
def celsius_to_fahrenheit(celsius: float) -> float:
    return celsius * 9 / 5 + 32
```

`def` تعریف، `snake_case` قرارداد نام‌گذاری، `: float` type annotation، `-> float` return annotation، تورفتگی **بخشی از دستور زبان** است.

**Python هیچ‌وقت type annotation ها را اجرا نمی‌کند.** `celsius_to_fahrenheit("hello")` اجرا می‌شود، `"hello" * 9` موفق می‌شود (تکرار رشته)، و بعد **وسط محاسبه** روی تقسیم می‌شکند.

پس چرا می‌نویسیم؟ برای انسان‌ها؛ برای ابزارها (`mypy`)؛ و برای FastAPI در Stage 4 که **تنها جایی است که annotation ها واقعاً اجرا می‌شوند**.

> **اعتبارسنجی باید در مرز انجام شود، نه در عمق.** خطا در عمق تابع رخ داد، نه در مرز ورودی — در کد واقعی یعنی traceback چهار لایه دورتر از محل ورود دادهٔ خراب را نشان می‌دهد.

### تکلیف باز

طراحی schema برای یک سطر CSV از سنسورهای یک pump صنعتی: ۵ تا ۸ ستون، با نام، type، دلیل، و محدودهٔ معتبر. و: وقتی سنسوری یک خواندن را از دست می‌دهد، آن سطر چه شکلی است؟

## راه‌اندازی روی ماشین دوم — Linux (2026-09-17)

پروژه حالا روی دو ماشین توسعه داده می‌شود: ویندوزِ شرکت و لینوکسِ شخصی. اولین بار که محیط را روی ماشین دوم ساختیم، شکست.

### تشخیص: pypi در دسترس نبود

```
ReadTimeoutError: HTTPSConnectionPool(host='pypi.org', port=443): Read timed out.
ERROR: No matching distribution found for setuptools>=68
```

جملهٔ آخر دروغ نیست، ولی **گمراه‌کننده** است: می‌گوید «نسخه‌ای پیدا نشد»، در حالی که واقعیت این بود که اصلاً به index وصل نشدیم. باز هم همان درس: *«چیزی پیدا نکردم» با «ثابت شد نیست» یکی نیست.*

فرضیه‌ها، و آزمایش هرکدام با یک دستور:

| فرضیه | آزمایش | نتیجه |
|---|---|---|
| کل اینترنت قطع است | `git clone` از GitHub | ✅ کار کرد — رد شد |
| کل دامنهٔ python بسته است | `curl files.pythonhosted.org` | `404` در ۱۰ ثانیه — یعنی TLS برقرار شد. رد شد |
| فقط `pypi.org` بسته است | `curl pypi.org/simple/pytest/` | timeout — **تأیید شد** |

`404` گرفتن یک **موفقیت** است: یعنی DNS، TCP و TLS همه کار کردند و سرور جواب داد. تنها مسیر اشتباه بود. در تشخیص شبکه، «چه نوع شکستی» از «شکست خورد» خیلی پرمعناتر است: `timeout` یعنی بسته‌ها گم شدند؛ `404` یعنی مکالمه انجام شد.

### مشکل دوم: flag به ارث نمی‌رسد

با mirror دوباره امتحان کردیم و **باز هم** شکست خورد:

```bash
pip install --index-url https://... -e ".[dev]"   # ❌
```

`pip install -e .` یک process فرزندِ pip می‌سازد تا build backend یعنی `setuptools` را نصب کند. آن فرزند **flag های خط فرمان را به ارث نمی‌برد** — پس دوباره سراغ `pypi.org` رفت و timeout خورد. همان قانون environment از بخش قبل، این بار به شکل یک باگ واقعی:

> فرزند یک کپی از **environment** والد می‌گیرد — نه از آرگومان‌هایش.

راه‌حل، همان تنظیم به شکل متغیر محیطی:

```bash
export PIP_INDEX_URL=https://mirror-pypi.runflare.com/simple/
pip install -e ".[dev]"    # ✅
```

**قاعدهٔ عملی:** وقتی ابزاری زیرفرایند می‌سازد، پیکربندی را با environment variable بده نه با flag.

### trade-off که باید آگاهانه بپذیری

mirror یک شخص ثالث است که کدی را به تو می‌دهد که قرار است **اجرا** کنی. `pip` پکیج را با امضای مستقل تأیید نمی‌کند؛ پس یک mirror خصمانه می‌تواند نسخهٔ دستکاری‌شده بدهد و هیچ هشداری نبینی. این یک supply-chain attack است.

کاهش ریسک واقعی: lock file با hash های pin شده (`pip install --require-hashes`) — در Stage 6. تا آن موقع، mirror را به‌صورت `export` در همان shell نگه دار، نه در `pip.conf` دائمی، تا هر بار یک **تصمیم قابل‌مشاهده** باشد نه یک پیش‌فرض فراموش‌شده.

### تفاوت‌های ماشین

| | ویندوز (شرکت) | لینوکس (شخصی) |
|---|---|---|
| فعال‌سازی venv | `.venv\Scripts\activate` | `source .venv/bin/activate` |
| مفسر بیرون از venv | `python` | `python3` (بدون `python`) |
| احراز هویت push | Git Credential Manager | کلید SSH |
| نسخهٔ Python | 3.13 | 3.14 |

اختلاف نسخهٔ Python **عمدی** است و مفید: `requires-python = ">=3.12"` یک بازه است نه یک pin. اگر روزی چیزی فقط روی یک ماشین بشکند، اولین فرضیه همین اختلاف است. این همان دلیلی است که CI روی چند نسخه تست می‌گیرد.

دامنهٔ پروژه به **RAN telemetry** تغییر کرد. دیتا: شمارنده‌های PM از یک اپراتور تجاری،

### چرا با `csv` شروع کردیم و نه pandas

pandas همان چیزی را پنهان می‌کرد که می‌خواستیم ببینیم. `pd.read_csv` بدون پرسیدن سه تصمیم گرفت:
type ستون را `float64` کرد، خالی‌ها را `NaN` کرد، و `mean()` را طوری تنظیم کرد که NaN را نادیده بگیرد.

```
df[rb].mean()             →  10.190     ← NaN نادیده گرفته می‌شود
df[rb].fillna(0).mean()   →   9.070     ← خالی = صفر
                                          ۱۲٪ اختلاف، بدون هیچ هشداری
```

> ابزار سطح بالا را وقتی استفاده کن که بدانی چه چیزی را پنهان می‌کند. قبل از آن، پرده است نه ابزار.

pandas ابزار تحلیل است. `csv` ردیف‌به‌ردیف می‌خواند و برای ingestion و برای فایل‌های بزرگ درست‌تر است.

### مفاهیم Python

**`with open(...)`** — context manager. بسته شدن فایل را تضمین می‌کند حتی اگر خطا رخ دهد.
بدون آن، روی سرورِ طولانی‌مدت descriptor ها نشت می‌کنند تا `Too many open files`.

**`csv.DictReader`** — هر ردیف را dict می‌دهد با نام ستون‌ها به‌عنوان کلید. برتری‌اش بر دسترسی با
شماره: اگر ستونی وسط فایل اضافه شود، کدِ مبتنی بر شماره **در سکوت** غلط می‌خواند؛ کدِ مبتنی بر نام
با `KeyError` بلند می‌شکند.

**`newline=""`** هنگام باز کردن CSV اجباری است — مدیریت پایان خط به ماژول `csv` سپرده می‌شود.

**همه‌چیز `str` است.** خالی به شکل `''` می‌آید، نه `None`. و `float('')` خطا می‌دهد.

**`repr` در برابر `str`** — برای دیدن دادهٔ نامرئی همیشه `{value!r}` در f-string:
`print("")` هیچ نشان نمی‌دهد، `print(repr(""))` می‌دهد `''`.

**truthiness** — `if x:` می‌پرسد «درست‌گونه است؟» نه «برابر است؟». این‌ها falsy اند:
`0` `0.0` `""` `[]` `{}` `None`. پس `if float(vol):` یعنی «اگر صفر نباشد» — برعکس `== 0`.

**`elif`** — Python اولین شرط درست را اجرا می‌کند و بقیه را رها. به همین دلیل
`if vol == "": ... elif float(vol) == 0:` هرگز `float("")` را اجرا نمی‌کند. **اول بررسی، بعد تبدیل.**

### باگ‌هایی که مرتکب شدم و درسشان

| باگ | چرا ساکت بود |
|---|---|
| `float(rb) == ""` | `float()` اول اجرا می‌شود و می‌ترکد — این یکی **بلند** بود |
| `vol == 0` | مقایسهٔ `str` با `int` → همیشه `False`، بدون خطا |
| `vol == "0"` | مقدار واقعی `"0.0"` است؛ مقایسهٔ رشته کاراکتربه‌کاراکتر است |
| شمارش در `if` بیرونی **و** داخلی | هر ردیف دو بار شمرده شد → جمع دقیقاً ۲× |
| برداشتن `float()` برای رفع خطا | خطا رفت، باگ ماند — و از بلند به **ساکت** تبدیل شد |

> **ساکت کردن خطا با حل کردنش یکی نیست.** راه دوم همیشه سریع‌تر است و همیشه گران‌تر.

### تشخیص از روی *شکلِ* عدد غلط

- جمع دقیقاً **۲ برابر** کل → هر ردیف دو بار شمرده شده (باگ ساختاری، نه مرزی)
- شمارنده دقیقاً `0` یا دقیقاً `total` → به **شرط** شک کن، نه به دیتا؛ احتمالاً همیشه False/True است
- شمارنده‌ای که در کد اصلاً ظاهر نمی‌شود → تعریف شده و فراموش شده

**همیشه جمع دسته‌ها را با کل چک کن.** ساده‌ترین تست دنیاست.
ولی: **تست فقط چیزی را که می‌سنجد تأیید می‌کند.** جمع درست بود در حالی که ردیف‌ها در خانهٔ غلط می‌افتادند.

### یافته: سه نوع «نبودنِ داده» در یک فایل

```
                 vol خالی      vol = ۰       vol > ۰
              ┌────────────┬────────────┬────────────┐
rb خالی       │   3,556    │  13,041    │      0     │
              ├────────────┼────────────┼────────────┤
rb عدد دارد   │      0     │     421    │  134,008   │
              └────────────┴────────────┴────────────┘
```

**۱. ردیف اصلاً وجود ندارد** — ~۸۷٪ از بازه‌های ۱۵ دقیقه‌ای. ۲٬۹۷۱ برچسب زمانی موجود در برابر
~۲۲٬۷۰۰ مورد انتظار. **هیچ `isnull()` ای این را پیدا نمی‌کند** — سلولِ خالی قابل شمردن است، ردیفِ نبوده نیست.

**۲. ردیف هست، همهٔ اندازه‌گیری‌ها خالی** — ۳٬۵۵۶ ردیف. فقط سه ستون هویت پر است. یک «اسکلت»:
سیستم می‌دانست باید اندازه می‌گرفت، نتوانست. `fillna(0)` روی این‌ها یعنی نوشتن
`Radio unit energy = 0` برای سایتی که روشن بوده — یک **جعل**.

**۳. ردیف هست، شمارندهٔ خاصی خالی** — ۱۳٬۰۴۱ ردیف. سلول بیکار. خرابی نیست، یک **پیام** است.

خانهٔ `rb خالی + ترافیک > 0` **صفر** است — در ۱۵۱٬۰۲۶ ردیف بدون استثنا.

### یافته: ۴۲۱ ردیف، و اینکه چرا ناهنجاری نیستند

یک اختلاف کوچک آماری (`10.190` در برابر `10.221`) ما را به ۴۲۱ ردیف رساند که RB عدد دارند ولی
حجم داده صفر است. مقایسه با گروه عادی (میانه، و درصد «دقیقاً صفر»، چون میانه توزیع را پنهان می‌کند):

```
                      عجیب      عادی
4G data volume UL      0.00     26.42     ۹۵٪ صفر → ترافیک uplink هم نبود
4G RRC users           0.00     10.41     ۵۴٪ صفر → کاربری وصل نبود
4G RB utilization      0.01      7.32
Radio unit energy     26.00     48.00
```

حدس اولیهٔ mentor (ترافیک control-plane با کاربر متصل) **رد شد**. توضیح درست از دانش دامنهٔ خودِ
یادگیرنده آمد و در `CLAUDE.md` ثبت شد: سلول بیکار یک **کف ساختاری** ۰.۵ تا ۲ درصدی دارد
(SIB، paging، اتصال‌های گذرا). عدد مطلق تقریباً ثابت است ولی مخرج با bandwidth بزرگ می‌شود،
پس همان رفتار روی سلول ۵ مگاهرتزی چهار برابر بزرگ‌تر دیده می‌شود.

> **شمارنده، scheduler را می‌سنجد نه رادیو را.** CRS و PSS/SSS و PBCH دائماً RE اشغال می‌کنند
> ولی معمولاً در PRB utilization نمی‌آیند. «فیزیکاً اشغال» و «آنچه KPI می‌شمارد» دو چیزند،
> و تفاوتشان را vendor تعریف می‌کند.

**نتیجهٔ معماری:** هرگز utilization خام را به مدل نده. baseline تجربی هر سلول را دربیاور و
انحراف از آن را feature بگیر.

### سؤالات باز

  (احتمال‌ها: NULL وقتی هیچ رویداد scheduling نبوده / sleep mode / نحوهٔ تجمیع)

  احتمالاً فقط bandwidth کوچک‌تر. در Stage 5 دوباره نگاه شود.
- تصمیم طراحی برای ۳٬۵۵۶ ردیف اسکلتی: دور ریختن، نگه‌داشتن با NULL، یا قرنطینه؟

### روش کار

**یک خط بنویس، اجرا کن، به خروجی نگاه کن.** هیچ‌وقت ده خط ننویس و بعد اجرا کن.
`dir(x)` چه چیزی موجود است · `help(x)` چطور استفاده شود · `type(x)` الان با چه چیزی طرفی.

**از سؤال شروع کن، نه از کد.** ندانستن اینکه از کجا شروع کنی یعنی داری از وسط شروع می‌کنی.
عقب بیا تا به چیزی برسی که بلدی.

**قبل از اجرا پیش‌بینی کن.** اگر درست درآمد، فهمیده‌ای. اگر نه، همان لحظه می‌دانی کجای مدل ذهنی‌ات غلط بود.

**قبل از اختراع توضیح، مستندات را بخوان** — و بعد واقعاً به‌کارش ببند. README از اول
دربارهٔ bandwidth هشدار داده بود و mentor فراموشش کرد.
